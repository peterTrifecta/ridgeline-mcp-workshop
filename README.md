# Ridgeline Outfitters MCP server

An example [MCP](https://modelcontextprotocol.io) server over the CRM and ERP
of a fictional wholesale outdoor-gear company. The business rules live in a
service; the MCP layer holds only guardrails on the AI. It was written for a
live walkthrough covering contract pricing, credit, open invoices and discount
approvals, and includes what is needed to replay it or to run the finished
server.

## Running it

Requirements: [uv](https://docs.astral.sh/uv/) (it fetches Python 3.11+ if
needed) and an Anthropic API key. No Node or npm. Developed and tested on
macOS.

```bash
git clone https://github.com/peterTrifecta/ridgeline-mcp-workshop.git
cd ridgeline-mcp-workshop
cp .env.example .env     # then put your key after ANTHROPIC_API_KEY=
uv run start             # builds the databases and opens the chat page
```

`uv run start` runs a local chat page at `http://127.0.0.1:8765` that talks to
Claude through the Anthropic API and shows every tool call. The key is read by
the Python backend and does not reach the browser. Model, effort and port are
set in `.env`; see `.env.example`.

A fresh checkout is the finished server: all seven tools and both AI
guardrails. Ask it anything from
[`snippets/prompts.txt`](snippets/prompts.txt). To build it up step by step
instead, see [Replaying the walkthrough](#replaying-the-walkthrough). To use it
from Claude Desktop, which needs no API key, see
[Using it in Claude Desktop](#using-it-in-claude-desktop).

## Replaying the walkthrough

[`WALKTHROUGH.md`](WALKTHROUGH.md) is the script: what to do, what to type and
what to expect at each step. The five steps are:

1. No tools: Claude cannot answer.
2. Connect the server.
3. Fix a vague tool description.
4. Add a tool.
5. Add an AI guardrail.

`uv run reset N` copies the checkpoint for step N over `ridgeline_tools.py`,
rebuilds the databases and sets whether the chat page starts with tools on or
off. Clicking **New conversation** in the chat page restarts the MCP server, so
it picks up a reset or an edit. `uv run reset solution` brings back the
finished server. After any `reset`, git shows `ridgeline_tools.py` as modified;
the committed version is the solution.

## Using it in Claude Desktop

The server runs over stdio, so Claude Desktop can start it directly. No API key
is needed. Claude Desktop uses your existing subscription, and the server does
not call the API itself.

Add this to `claude_desktop_config.json`
(*Settings → Developer → Edit Config*):

```json
{
  "mcpServers": {
    "ridgeline": {
      "command": "uv",
      "args": ["run", "--directory", "/absolute/path/to/this/repo",
               "ridgeline-mcp"]
    }
  }
}
```

Restart Claude Desktop and ask it about Summit Trail Co. The databases are
built on first use.

## What's in it

| | |
|---|---|
| `crm.db` | Mock CRM: accounts, reps, products, orders, discount requests |
| `erp.db` | Mock ERP: customers, invoices, credit limits, terms |
| `pricing_service.py` | All the business rules. Stands in for a Pricing & Credit process API |
| `ridgeline_tools.py` | The MCP server. Tool descriptions, one service call per tool, AI guardrails |
| `policies.md` | The same rules written out in English |
| `workshop/` | The local chat page |
| `checkpoints/` | `ridgeline_tools.py` as it looks at the start of each step |
| `snippets/` | The code pasted in during each step, plus every prompt in order |
| `tests/` | The expected answers, as automated tests |
| `WALKTHROUGH.md` | The step-by-step script: what to do, type and expect at each step |

There are two databases so the two systems are visible as two files. Both are
generated by `data/generate.py` from `data/model.py`, are gitignored, and are
built on first run.

### Where the rules live

`pricing_service.py` holds every business rule: contract tiers, account
standing, credit, payment terms, discount approvals. In a real deployment this
would be the CRM's approval process, the ERP, or a process API over both.

`ridgeline_tools.py` holds none of them. Each tool is a description and a single
call into the service. The only rules in this file are rules about the AI:

- it must get explicit confirmation before submitting a discount request;
- it can auto-approve up to 5%. A sales rep can approve 10%.

These are not company policy. They are limits on what the AI may do on its own.
Everything else is enforced in the service, so a rep in the CRM and a partner in
the portal get the same answer.

## Commands and dates

```bash
uv run check             # one PASS/FAIL line per check
uv run test              # the expected answers, as automated tests
uv run reset 3           # jump to the start of step 3 (1-5, or `solution`)
uv run smoke             # the model-dependent cases (calls the API; costs a few cents)
```

All dates in the data are offsets from today ("issued 20 days ago"), so the
answers are the same on any day. The databases rebuild if they were built on an
earlier day. To use a specific day:

```bash
AS_OF=2026-10-07 uv run start
```

## Adapting it

To point this at your own data, change:

- `data/model.py`: the accounts, products, orders and invoices;
- `pricing_service.py`: the rules (or replace it with calls to the systems that
  already hold your rules);
- `ridgeline_tools.py`: the tool names and descriptions;
- `tests/`: the expected answers.

## Taking it further

This server runs locally, which suits a walkthrough but not production. A
production deployment is a hosted (remote) MCP server behind your SSO, added
once by an admin as an org-wide connector, or an MCP layer on the platform
where your APIs already live: your CRM's own MCP support, or your integration
platform.

For your own systems, point something like `pricing_service.py` at the systems
that already hold the rules, and expose a narrow, governed action on top of it.
